## Problem Statement

用户连接 SSH、WSL 或 Docker 设备后，ZCode 在远端运行一个常驻的远端服务（daemon：Supervisor、Server Core
与 Agent 进程）。桌面端只能连接和断开，断开后远端服务继续运行。UI 上没有任何停止或重启它的方式。

- 远端服务卡死、状态错乱，或 Core 反复崩溃进入 `crash-loop-stopped` 后，自动恢复一直失败，设备停在“连接失败”。
  用户只能自己登录服务器找进程手动 kill，或执行不熟悉的 `zcode restart`。而现有 `zcode restart` 只重启 Core，
  daemon 未运行、Supervisor 已死但有残留时直接失败，不能用来自救。
- 用户在共享服务器上用完后，想停掉远端服务释放内存和 CPU，或满足运维对常驻进程的限制，但 UI 没有入口。
  “断开”只关闭本机连接，远端服务和任务继续运行。
- 用户在远端手动执行 `zcode stop` 后，本机的自动恢复会在几秒内执行 `serve --daemon`，把服务重新拉起。
- 现有 `zcode stop` 只回 ack，不等停止完成。由桌面端串联 `stop` 和 `serve --daemon` 会出现“报告成功，
  但最终没有远端服务在运行”的竞态。

## Solution

在「设置 › 远程设备」设备卡的「更多」菜单中增加「重启远端服务」和「停止远端服务」。这是唯一入口。

- **重启**：重启整台设备上的远端服务（Supervisor 和 Core 都换成新进程），完成后自动连接。可从已连接、
  未连接、连接失败状态发起，主要用于自救。
- **停止**：本机先停止自动恢复并断开，再停掉远端服务。设备变为“未连接”。之后用户点“连接”时，照常拉起远端服务。
- 两个操作都先弹危险确认，列出将被中断的运行中任务。
- 时序由远端 CLI 负责。`zcode stop --wait` 等到真正停止才返回；`zcode restart` 改为整棵进程树重启，
  能从 `crash-loop-stopped` 恢复。桌面端只执行一条命令，命令返回就是最终结果。
- 只在桌面端提供。手机远控和 Web 端只被动显示断线与恢复状态。
- 停止不留持久标记。下次打开 ZCode 是否自动重连（并因此拉起远端服务），仍由「启动时自动重连」开关决定。

```text
设备卡「更多」 ─▶ 读取运行中任务 ─▶ 危险确认 ─▶ 管理服务 ─▶ Host 连接管理器
                                                          │
   停止：先断开（删除恢复意图）→ 未连接 ─────────────────────┤
   重启：登记生命周期操作 flight（断线视为预期）→ 连接中 ──────┤
                                                          │ transport exec（SSH / WSL / Docker）
                                                          ▼
                 远端 bin/zcode   stop --wait：锁释放且状态为 stopped 后返回
                                  restart：停止整棵进程树 → serve --daemon → ready 后返回
                                                          │
   停止：保持未连接  ◀─────────────────────────────────────┤
   重启：走现有连接流程 → 已连接，移除 flight  ◀────────────┘
```

可用状态：

| 设备状态                                 | 重启远端服务                   | 停止远端服务   |
| ---------------------------------------- | ------------------------------ | -------------- |
| 已连接                                   | 可用；完成后重新连接           | 可用；变为未连接 |
| 未连接（用户断开）                       | 可用；完成后连接               | 可用；保持未连接 |
| 连接失败（恢复预算耗尽）                 | 可用；完成后连接               | 可用；变为未连接 |
| 连接中 / 更新中 / 本设备有其他操作进行中 | 禁用                           | 禁用           |
| 需要处理（需安装 / 需升级 / 身份待确认 / 需要凭据） | 隐藏                | 隐藏           |
| 已知远端版本低于本合同首个版本或版本未知 | 禁用，提示“更新远端服务后可用” | 同左           |

## User Stories

### 自救：重启

1. 作为桌面端用户，我希望在设备卡「更多」菜单里找到「重启远端服务」，以便远端服务异常时不用登录服务器手动处理。
2. 作为桌面端用户，我希望设备显示“连接失败”时也能重启远端服务，以便自动恢复反复失败时自己恢复。
3. 作为桌面端用户，我希望设备“未连接”时也能重启远端服务，以便不必先连上卡死的服务。
4. 作为桌面端用户，我希望重启完成后 ZCode 自动连接这台设备，以便重启后直接继续工作。
5. 作为桌面端用户，我希望远端 Core 反复崩溃后，重启能让服务重新运行，以便走出崩溃保护状态。
6. 作为桌面端用户，我希望重启后已打开的远程项目和会话自动挂回、历史仍在，以便继续原来的任务。
7. 作为桌面端用户，我希望重启期间设备显示“连接中”，不出现失败或重试计数，以便知道操作还在进行。
8. 作为桌面端用户，我希望重启只在远端服务真正就绪后才开始连接，以便不会连到正在退出的旧进程。

### 释放资源：停止

9. 作为共享服务器上的用户，我希望在设备卡上停止远端服务，以便用完后释放服务器的内存和 CPU。
10. 作为桌面端用户，我希望停止后设备显示“未连接”，ZCode 不会在几秒后把服务自动拉起，以便停止真正生效。
11. 作为桌面端用户，我希望设备已经断开时也能停止远端服务，以便处理断开后仍在运行的服务。
12. 作为桌面端用户，我希望停止后点一次“连接”就能照常启动远端服务，以便需要时恢复使用。
13. 作为桌面端用户，我希望停止命令等远端真正停止后才报告完成，以便“已停止”的提示是真实的。
14. 作为桌面端用户，我希望下次打开 ZCode 时是否自动重连仍只由「启动时自动重连」开关决定，以便用一个开关控制启动行为。
15. 作为开启了启动自动重连的用户，我希望停止确认里提示“下次打开 ZCode 会重新启动远端服务”，以便知道停止只对当前这次运行有效。

### 确认与影响

16. 作为桌面端用户，我希望停止和重启前都弹出确认，以便避免误触中断工作。
17. 作为桌面端用户，我希望确认弹窗默认聚焦“取消”，回车不会执行，以便不会因误按回车中断任务。
18. 作为有运行中任务的用户，我希望确认弹窗列出将被中断的任务，以便判断能否停止。
19. 作为用户，我希望弹窗说明被中断的任务不会自动续跑，以便知道之后要手动重新发送。
20. 作为用户，我希望远端没有提供任务清单时，弹窗仍说明会中断所有运行中任务，以便不误以为没有影响。
21. 作为多台电脑连接同一台服务器的用户，我希望弹窗提示其他电脑上的 ZCode 可能重新启动远端服务，以便理解停止后服务为何又在运行。

### 失败与反馈

22. 作为桌面端用户，我希望操作成功时看到提示，并在设备卡“最近日志”里留下一条记录，以便事后确认做过什么。
23. 作为桌面端用户，我希望重启失败时看到错误提示，原本有恢复意图的设备继续走现有自动恢复，以便不额外操作也有机会恢复。
24. 作为桌面端用户，我希望停止失败时看到错误提示，设备保持“未连接”并可再试一次，以便处理远端暂时无响应的情况。
25. 作为桌面端用户，我希望远端服务无响应时看到明确的“远端服务无响应”提示，以便知道需要登录服务器处理。
26. 作为 SSH 密码未保存的用户，我希望看到与更新远端服务相同的补充凭据提示，以便知道先连接一次。
27. 作为 Docker 用户，我希望容器已停止时看到命令执行失败的说明，以便先启动容器。

### 可用性与门禁

28. 作为桌面端用户，我希望连接中、更新中或本设备有其他操作时这两项显示为禁用，以便不与进行中的操作冲突。
29. 作为桌面端用户，我希望设备需要安装、升级或确认身份时不显示这两项，以便先处理主操作。
30. 作为远端版本较旧的用户，我希望这两项禁用并提示“更新远端服务后可用”，以便知道如何获得该能力。
31. 作为中英文用户，我希望菜单、弹窗和提示都有对应语言的文案，并统一称为“远端服务”，以便不接触 daemon 等术语。
32. 作为深色或浅色主题用户，我希望“停止远端服务”以危险样式显示且清晰可辨，以便识别它的影响。

### 范围与一致性

33. 作为手机远控用户，我希望桌面停止或重启远端服务后，手机端显示断线与恢复状态，以便知道远程任务的情况。
34. 作为 SSH、WSL、Docker 用户，我希望三种连接方式的行为一致，以便不用区分。
35. 作为 WSL 或 Docker 用户，我希望重启后远端服务仍以原方式运行、不注册系统服务，以便不改变发行版或容器的环境。
36. 作为在终端管理服务器的用户，我希望 `zcode stop --wait` 和 `zcode restart` 同样可用，以便在脚本中可靠地停止或重启服务。
37. 作为通过 OS service 运行远端服务的用户，我希望停止后服务管理器不会自动拉起它，重启后仍由服务管理器托管，以便启动方式保持不变。

## Implementation Decisions

### 远端 Server CLI

- `stop --wait`：发出 stop 后等待“data-root 锁已释放且 status 为比基线新的 stopped”，复用升级 handoff 的停止等待
  与 20 秒统一上限。daemon 原本未运行时立即成功；Supervisor 进入 `stop-failed` 时失败。不带 `--wait` 的旧行为保留。
- `restart` 改为整棵进程树重启，由发起命令的 CLI 进程协调，与 update handoff 一样不在持锁的 Supervisor 进程内自举：
  1. daemon 在运行时，按 `stop --wait` 停止现有 Supervisor；未运行时跳过；
  2. 以 current release 执行 `serve --daemon` 并等待 ready；
  3. 保持原启动方式：OS service 继续由服务管理器托管，跳过服务注册的环境（WSL、Docker）继续 detached fallback。
- `restart` 能从 `crash-loop-stopped`、`stop-failed` 且 `pid:null`、Supervisor 已死但残留锁或 socket 的状态恢复；
  新 Supervisor 重置崩溃预算。不检查运行中 Task，不自动恢复被中断的 Task。
- Supervisor 控制协议删除 `restart`：它只重启 Core，唯一调用方是旧 `zcode restart`。
- control 请求超时时返回新的公开错误码 `source-server-control-unresponsive`，不强杀 Supervisor（见 R3-ISSUE-032）。
  `stop-failed` 返回新的公开错误码 `source-server-stop-failed`。启动阶段失败沿用 `serve --daemon` 的现有错误分类。
- 成功时 `stop --wait` 与 `restart` 输出最终 ServerStatus JSON；失败沿用 `{ok:false,error,code?,retryable?}`。

### Transport Adapter

- 非 SSH 执行 `restart` 时，与 `serve --daemon` 一样加跳过服务注册的环境变量，避免在容器或 WSL 中注册 systemd 服务。
- 桌面端只执行固定 argv：`stop --wait --json`、`restart --json`、`running-tasks --json`。

### Host 连接管理器

- 新增按设备的停止、重启和读取运行中任务三个能力。路由由 Host 按 `sourceServerId` 选择（更新仍由 Renderer 传
  `profileId`，不改）：设备在线时用在线连接；否则用默认连接，再按最近连接时间选择可静默取得凭据的连接（与启动静默重连
  候选同一排序）。凭据不可静默取得时返回 `credentials-required`。
- **停止**：在执行远端命令前，先完整走一次断开收口（清定时器、中止在途连接与更新、删除恢复意图、释放连接、置 offline），
  再执行 `stop --wait`。恢复意图已删除，所以 WS 断开不会排重试，离线探测也不会运行。成功和失败都保持 offline；
  失败原因通过操作结果、日志和 toast 呈现。
- **重启**：把现有的更新 in-flight 机制泛化为“生命周期操作 flight”，同时覆盖更新与重启。flight 存在时，
  当前在线连接的关闭被视为预期断线，只做连接失效，不排重试。命令成功后走现有连接流程并发出重连事件，
  让 Registry 为已打开的 workspace 换代；最后移除 flight。
- **重启失败**：原本有恢复意图且不是终态时，与更新失败相同，从第一档开始现有自动恢复；没有恢复意图时
  （从未连接状态发起）置为 `failed`，显示连接失败，不启动自动恢复。更新失败且没有恢复意图时仍为 `offline` 带错误，不改。
- 同一设备的生命周期操作互斥：重启或停止进行中时拒绝任何新的生命周期操作（更新、重启、停止）；更新进行中时拒绝重启与停止；多个更新并存
  （经 sibling Profile 发起）保持现状。用户断开或移除设备会中止进行中的重启 flight。
- 重启期间不新增 Host 连接状态，投影为“连接中”；进度说明写入设备操作日志。
- 不使用超时等待同步本机状态，完成判定只来自远端命令结果和现有连接流程。

### 管理服务（Host ↔ Renderer）

- `ISourceServerManagementService` 新增 `stopSource(sourceServerId)`、`restartSource(sourceServerId)`、
  `getSourceRunningTasks(sourceServerId)`，入参和返回值有严格运行时 schema。
- 能力只在桌面 Renderer 开放；手机 attachment 的 RPC allowlist 不增加这些方法。
- 操作写入所用连接的设备操作日志：开始、成功、失败各一条，失败附原因。

### 设备卡 UI

- 两个菜单项位于「设备信息」「复制设备 ID」之后、「移除设备」之前，用分隔线单独成组；
  「停止远端服务」使用 destructive 菜单项样式。
- 可用状态按 Solution 表格计算；“需要处理”按五态模型的 `pending` 判断，含需要凭据。版本门禁比较设备记录中最近一次
  握手的远端版本与本合同首个版本常量；版本缺失按不支持处理。不发命令试探：旧 CLI 收到未知命令会转交 TUI，可能卡住。
  “更新远端服务后可用”以一行小号弱化文字显示在禁用菜单项内，不依赖悬停。
- 补充凭据提示：新增 `settings.source.error.credentials-required` 文案（大意“无法自动取得 SSH 凭据，请先连接一次此设备”），
  设备卡内联错误与失败 toast 共用；更新遇到同一错误码时也使用它。
- 点击后先读取运行中任务，再打开 destructive 确认。弹窗说明由以下部分组成：
  - 中断说明：会中断此设备上所有运行中任务，任务不会自动续跑；
  - 任务清单：复用强制更新的清单展示；读不到清单时显示“设备未提供任务清单”；
  - 其他客户端：其他电脑上的 ZCode 若连着这台设备，可能重新启动远端服务；
  - 仅停止且「启动时自动重连」开启时：下次打开 ZCode 会重新启动远端服务。
- 确认后调用管理服务，复用设备卡按 `source:<id>` 的同设备互斥。成功与失败都给 toast，失败 toast 可打开该设备的失败详情和最近日志。
- 所有文案使用“远端服务”，不出现 daemon、Supervisor、Core；中英文 key 同步补齐。英文新文案统一用 “remote service”，
  存量文案不改。

## Testing Decisions

- 好的测试只断言切面外部可观察的行为：CLI 的退出码、JSON 输出和真实进程状态；连接管理器公开 API 产生的状态事件与
  transport 调用；设备卡的 DOM 与管理服务调用。不断言私有字段和内部调用顺序。
- 先写测试并确认失败，再实现。

使用四个现有切面，不新增切面：

1. **Server CLI 命令**（先例：CLI 对未运行 daemon 执行 stop 的测试、update handoff 测试）
   - `stop --wait` 在锁释放前不返回；daemon 未运行时立即成功；`stop-failed` 时返回对应错误码；
   - `restart` 分别从 ready、未运行、`crash-loop-stopped`、Supervisor 已死但有残留四种状态出发，最终都有新的
     Supervisor 与 Core 处于 ready，崩溃预算重置；
   - control 无响应时返回 `source-server-control-unresponsive`，不 kill 任何进程；
   - 保持原启动方式：跳过服务注册的环境下不注册服务。
2. **Host 连接管理器 + 假 transport adapter**（先例：更新 flight、显式断开、retry 与终态恢复的现有测试）
   - 停止：远端命令执行前恢复意图已删除；WS 关闭后不排重试、不进入离线探测；结果为 offline；
   - 重启：flight 期间 WS 关闭不排重试；命令成功后发起连接并发出重连事件；失败时按是否有恢复意图分别收口；
   - 互斥：更新、重启、停止并发时只有一个执行；断开或移除设备会中止重启；
   - 路由与凭据：离线设备按默认连接执行；凭据不可静默取得时返回 `credentials-required`；
   - 非 SSH 的 `restart` argv 带跳过服务注册的环境变量。
3. **设备卡组件 + 假管理服务**（先例：强制更新确认与任务清单的现有测试）
   - 五态与版本门禁下两个菜单项的显示、禁用、隐藏；
   - 确认弹窗的文案分支：有任务、无清单、启动自动重连开关开或关；取消不调用服务；
   - 成功与失败的 toast，失败可打开详情；中英文 key 一致。
4. **桌面 R3 daemon E2E**（先例：daemon detached 用例，SIGKILL 后重连拉起新进程）
   - 从设备卡「更多」停止：远端 Supervisor 与 Core 进程退出，设备显示“未连接”，等待一个自动重试周期后仍未被拉起；
   - 从设备卡「更多」重启：Supervisor 与 Core 的 pid 都变化，设备回到“已连接”，已打开会话可以继续发送。

- 手机端只被动显示断线状态，复用现有断线 E2E，不新增用例。
- 新增或修改的 E2E 同步更新 case 目录和覆盖矩阵。

## Out of Scope

- 手机远控和 Web 端的停止、重启入口。
- 侧栏项目行、会话断线横幅、失败详情弹窗中的入口。
- Supervisor 自身卡死时强杀 Supervisor 的兜底（R3-ISSUE-032）。
- `crash-loop-stopped` 时自动恢复无法拉起远端服务的缺陷，以及是否把它映射为“需要处理”（R3-ISSUE-031）。
- 持久的“用户已停止”标记，以及阻止其他客户端重新拉起远端服务。
- 远端服务的 pid、运行时长、资源占用等状态展示。
- 清理远端旧 release、卸载远端服务。
- 在 CLI 的 `stop`、`restart` 上增加运行中任务守卫。
- 启动自动重连“最近 7 天”文案与代码不一致（R3-ISSUE-033）。

## Further Notes

- 选择 transport exec 而不新增 Core 端点：生命周期 owner 是 Supervisor，Core 不能重启自己；自救时 Core 往往已不响应，
  而 transport exec 不依赖 Core。更新流程已使用同一通道。
- 选择由 CLI 负责时序：`stop` 只回 ack，status 写成 stopped 时锁还未释放，桌面端看不到可靠的完成信号。
- 其他客户端（另一台电脑上的 ZCode）的自动恢复可能在停止后几秒内重新拉起远端服务。产品一期按单窗口验收，
  首期只在确认弹窗中说明。
- 本合同首个版本取 `3.17.0`，作为桌面端常量参与版本门禁；不提升最低兼容版本。3.17.0 是首个包含本合同的正式版。
